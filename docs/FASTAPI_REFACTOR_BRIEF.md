# Развитие backend Formaslov

## Контекст

Formaslov изначально разрабатывался как MVP на Django и Django REST Framework. На этом этапе основная задача backend была достаточно классической: работа с пользователями, исследовательскими проектами, текстовыми материалами, разметкой, категориями, метками и экспортом результатов.

Для текущего объёма задач Django подходил хорошо и позволил быстро собрать рабочую версию продукта.

Сейчас проект готовится к следующему этапу развития. Планируется работа с большими наборами исследовательских материалов, пакетная загрузка документов и появление более длительных операций, которые не стоит выполнять внутри обычного HTTP-запроса. Кроме того, в дальнейшем предполагается добавить функции автоматизированной обработки текста и AI/NLP-интеграции.

Поэтому backend постепенно переводится на FastAPI и более явно разделяется на API, работу с данными и фоновые задачи.

## Почему FastAPI

Переход на FastAPI не связан с тем, что существующие задачи невозможно решить на Django.

FastAPI выбран для следующего этапа проекта по нескольким причинам:

- приложение становится более API-ориентированным;
- ожидается больше I/O-bound операций;
- удобна асинхронная работа с базой данных и внешними сервисами;
- Pydantic позволяет явно описывать входные и выходные данные API;
- OpenAPI-схема и Swagger-документация генерируются автоматически;
- структура приложения может оставаться достаточно компактной и собираться только из необходимых компонентов.

При этом основная цель миграции — не смена фреймворка сама по себе, а подготовка backend к расширению функциональности.

## Что меняется сейчас

Главная новая пользовательская функция — пакетная загрузка исследовательских материалов.

Пользователь сможет загрузить ZIP-архив с несколькими документами, например с набором интервью. API примет архив и создаст задачу на обработку, после чего пользователь сможет продолжить работу с приложением, не ожидая завершения импорта в рамках одного HTTP-запроса.

На первом этапе планируется поддержка `.txt` и `.docx`.

Обработка архива включает:

- проверку загруженного файла;
- распаковку;
- разбор документов;
- извлечение текста;
- создание материалов внутри проекта;
- сохранение информации об ошибках отдельных файлов;
- отображение общего статуса обработки.

По похожему принципу планируется вынести в фон и формирование крупных экспортов исследования.

## Фоновая обработка

Для длительных операций используется Celery.

FastAPI отвечает за HTTP API и создание задания, а сама обработка выполняется отдельным worker-процессом.

RabbitMQ используется как брокер сообщений между API и Celery workers.

Упрощённо процесс выглядит так:

```text
Пользователь
    |
    v
FastAPI
    |
    | создаёт задачу
    v
RabbitMQ
    |
    v
Celery worker
    |
    v
PostgreSQL / файлы
```

На текущем этапе через фоновые задачи будут выполняться:

- пакетный импорт документов;
- формирование экспортов.

В дальнейшем этот же механизм можно использовать для более длительной обработки текстов, внешних интеграций и AI-задач.

## Redis

Redis добавляется как отдельный слой кэширования.

На первом этапе он будет использоваться только там, где это даёт понятную пользу — например, для часто запрашиваемых категорий, меток или других редко изменяющихся данных проекта.

PostgreSQL при этом остаётся основным источником данных.

Redis не должен использоваться просто ради наличия технологии в проекте: кэширование добавляется только для конкретных read-heavy сценариев и с понятной инвалидизацией при изменении данных.

## Предполагаемая инфраструктура

После завершения текущего этапа backend будет выглядеть примерно так:

```text
Frontend
    |
    v
FastAPI
    |
    +------ PostgreSQL
    |
    +------ Redis
    |
    v
RabbitMQ
    |
    v
Celery workers
```

Основные роли компонентов:

**FastAPI** — REST API, валидация данных, авторизация, работа с БД и запуск фоновых задач.

**PostgreSQL** — основное постоянное хранилище.

**Redis** — кэширование часто читаемых данных.

**RabbitMQ** — очередь сообщений для фоновых задач.

**Celery** — обработка операций, которые не должны выполняться внутри HTTP-запроса.

Для локальной разработки инфраструктура запускается через Docker Compose.

## Что планируется в будущем

Архитектура должна позволить постепенно добавить новые задачи без повторного переписывания backend.

Возможные направления развития:

- автоматическая суммаризация интервью;
- предложение категорий или кодов для текстовых фрагментов;
- предварительная обработка больших наборов материалов;
- семантический поиск;
- интеграции с внешними AI/NLP-сервисами;
- хранение документов во внешнем object storage;
- более подробное отображение прогресса длительных операций.

Эти функции не входят в текущий этап разработки. Сейчас важно только заложить достаточно простую основу, в которую их можно будет добавить позже.

## Ограничения подхода

При рефакторинге важно не усложнять проект без необходимости.

Не планируется заранее строить микросервисную архитектуру, добавлять сложные паттерны, отдельные сервисы для каждой небольшой операции или создавать абстракции, которые пока нигде не используются.

Основной принцип разработки:

> сначала решать текущую задачу самым простым поддерживаемым способом, а расширять архитектуру только тогда, когда появляется реальная необходимость.

Также важно сохранить существующие пользовательские сценарии Formaslov и по возможности не менять API-контракты без причины.

## Результат текущего этапа

После завершения миграции проект должен:

- работать на FastAPI;
- использовать PostgreSQL через SQLAlchemy;
- поддерживать асинхронные I/O-операции;
- иметь актуальную OpenAPI-документацию;
- использовать Redis для реального кэширования;
- выполнять длительные операции через Celery;
- использовать RabbitMQ как брокер сообщений;
- поддерживать пакетную загрузку документов;
- формировать крупные экспорты в фоне;
- сохранять существующую основную функциональность Formaslov.

Главная цель — получить более подходящую для дальнейшего развития backend-основу, не превращая проект в чрезмерно сложную систему раньше времени.
